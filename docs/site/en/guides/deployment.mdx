Verify a foreground connection first. On Linux, systemd can manage the server and journald can collect its logs.

## Prepare the files and user

Create a dedicated `umbra` user. Install the binary at `/usr/local/bin/umbra` and the configuration at `/etc/umbra/server.toml`. Only the service user and administrators should read it. Adjust the absolute paths and user below to match your installation.

## Configure the network

Open the TCP port configured in `listen`. For QUIC, also configure `udp_listen` and open the matching UDP port. If a layer-4 frontend owns the public port, bind Umbra to loopback and forward TCP/QUIC transparently. Keep backend ports private. This requires transport-aware forwarding rather than an ordinary HTTP reverse-proxy configuration.

## Create the service

Save as `/etc/systemd/system/umbra-server.service`:

```ini
[Unit]
Description=Umbra Server
After=network-online.target
Wants=network-online.target

[Service]
Type=simple
User=umbra
ExecStart=/usr/local/bin/umbra server -c /etc/umbra/server.toml
AmbientCapabilities=CAP_NET_BIND_SERVICE
NoNewPrivileges=true
Restart=on-failure
RestartSec=5
LimitNOFILE=65535

[Install]
WantedBy=multi-user.target
```

`CAP_NET_BIND_SERVICE` permits binding low ports such as 443. Check the user, file paths and permissions before enabling the service.

## Start and inspect

```sh
sudo systemctl daemon-reload
sudo systemctl enable --now umbra-server
sudo journalctl -u umbra-server -f
```

Make a client request to confirm background operation works.

## Plan resources and maintenance

Current throughput tuning assumes at least 1 GiB of server RAM. Leave room for the OS, kernel buffers and other services when setting application budgets. Diagnostics are disabled by default; enable them when investigating a problem. Restart after configuration changes and verify a request. Keep the previous binary and configuration for rollback.
