`transport` は TCP 要求の伝送方式です。`udp_transport` で UDP だけ別経路を選べます。省略時は `transport` を継承します。


## 結果を確認するには

最初の接続には TCP を選びます。両端で動作を確認してから QUIC や TCP/UDP の別経路を試してください。設定は 1 項目ずつ変更し、同じアプリで再確認します。Umbra は伝送方式を自動では切り替えません。

## 最初に選ぶモード

初回接続や UDP が使えない環境では TCP を選びます。接続を再利用するなら mux を有効にし、独立 Vision なら無効にします。UDP が使える場合、特に TCP が注入された RST で切断される環境では QUIC を試せます。両経路を使うには TCP と `udp_transport = "quic"` を設定します。まず到達性を確認し、同じアプリで遅延、安定性、転送量を比較します。

## TCP 接続の再利用

```toml
transport = "tcp"
mux = true
```

要求は暗号化接続を共有します。適応型ウィンドウは消費量と往復時間に追従し、予算内で動作します。共有 TCP でパケットが失われると、同じ接続の要求が待つことがあります。両端で互換バージョンを使ってください。

## 独立 TCP / Vision

```toml
transport = "tcp"
mux = false
```

要求ごとに接続を用意します。認証協議後、適用可能な TLS 1.3 レコードは外側の暗号化や追加フレームなしで転送されます。他の通信は暗号化が続きます。アプリの HTTPS は有効にしてください。転送はユーザー空間で行われ、性能は端末とネットワークに依存します。

## QUIC

```toml
transport = "quic"
```

QUIC は UDP 上で動きます。`udp_listen` とポートを有効にし、到達可能な QUIC サイトを使います。別々のストリームは独立して損失を回復しますが、各信頼性ストリーム内では順序を維持します。Umbra の UDP 関連付けも信頼性 QUIC ストリームで運ぶため、損失時に後続データが待つ場合があります。

既定は Quinn BBR で、`cubic`、`new-reno` も選べます。本端の QUIC 送信に作用し、OS の TCP 設定とは独立しています。

## 二つの経路を一つの入口で

クライアント：

```toml
transport = "tcp"
udp_transport = "quic"
mux = false
socks_listen = "127.0.0.1:1080"
```

サーバー：

```toml
listen = "0.0.0.0:443"
udp_listen = "0.0.0.0:443"
```

他の必須設定も維持します。アプリは一つの SOCKS5 を利用します。Clash の `udp: true` は UDP を許可し、TCP は `transport` に従います。ネットワークが変わったら手動で設定を変更します。自動 TCP/QUIC 切り替えはありません。

## パディングとハンドシェイクの書き込み

パディングは接続初期にランダム長のデータを追加し、その後は頻度を下げます。固定長パターンを弱める一方、帯域を消費します。`tcp_evasion = "segment"` は ClientHello を順序付き書き込みに分割し、実際のパケット境界は OS が決定します。互換性問題では `off` を試せます。Geneva DSL は非対応です。
