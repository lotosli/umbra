前面での接続確認後にサービス化します。Linux では systemd でプロセスを管理し、journald でログを確認できます。


## 結果を確認するには

デプロイ後、別のクライアントからクイックスタートの curl コマンドを実行し、ページが返ることを確認します。続いてサービスを再起動し、同じ確認を繰り返します。これでリモート接続、設定ファイルの読み取り、再起動後の復旧を確認できます。

## ユーザーとファイルを準備

専用ユーザー `umbra` を作り、プログラムを `/usr/local/bin/umbra`、設定を `/etc/umbra/server.toml` に配置します。読み取りはサービスユーザーと管理者に限定します。絶対パスとユーザー名は環境に合わせて変更してください。

## ネットワークを設定

`listen` の TCP ポートを開きます。QUIC では `udp_listen` と UDP ポートも必要です。公開ポートを L4 フロントエンドが使う場合は Umbra をループバックにバインドし、TCP/QUIC を透過転送します。内部ポートは非公開に保ちます。通常の HTTP リバースプロキシ設定とは異なり、該当トランスポートの転送が必要です。

## サービスを作成

`/etc/systemd/system/umbra-server.service` に保存します。

```ini
[Unit]
Description=Umbra Server
After=network-online.target
Wants=network-online.target

[Service]
Type=simple
User=umbra
ExecStart=/usr/local/bin/umbra server -c /etc/umbra/server.toml
AmbientCapabilities=CAP_NET_BIND_SERVICE
NoNewPrivileges=true
Restart=on-failure
RestartSec=5
LimitNOFILE=65535

[Install]
WantedBy=multi-user.target
```

`CAP_NET_BIND_SERVICE` は 443 などの低位ポートを利用するための権限です。起動前にユーザー、パス、権限を確認します。

## 起動とログ確認

```sh
sudo systemctl daemon-reload
sudo systemctl enable --now umbra-server
sudo journalctl -u umbra-server -f
```

その後、クライアントからリクエストを送って確認します。

## リソースと保守

現在のスループット最適化は、サーバーに少なくとも 1 GiB の物理メモリがあることを前提とします。OS、カーネルバッファー、他のサービス用にも余裕を残してください。診断は通常無効で、問題を調べる際に有効化します。設定変更後は再起動して確認し、戻せるよう以前のプログラムと設定を保管します。
