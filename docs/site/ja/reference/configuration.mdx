まず既定値で接続し、再現できる負荷で比較します。両端は `[performance]` を受け付けます。

## 既定値とフィールド

```toml
[performance]
memory_mib = 512
group_memory_mib = 256
max_window_mib = 64
quic_stream_window_mib = 6
quic_send_window_mib = 32
adaptive_mux = true
diagnostics_interval_secs = 0
quic_congestion = "bbr"
```

| 項目 | 既定値 / 要件 | 意味 |
|---|---|---|
| `memory_mib` | `512` | プロセスの論理メモリ予約。16〜16384 MiB |
| `group_memory_mib` | `256` | 資格情報グループ上限。16 MiB〜プロセス上限 |
| `max_window_mib` | `64` | 適応型の合計ウィンドウ上限。1〜64 MiB |
| `quic_stream_window_mib` | `6` | QUIC ストリーム受信ウィンドウ。1〜64 MiB |
| `quic_send_window_mib` | `32` | QUIC 送信保存量。1〜64 MiB |
| `adaptive_mux` | `true` | 新クライアント TCP mux の適応制御 |
| `diagnostics_interval_secs` | `0` | サーバー診断間隔。0で無効、1〜3600秒 |
| `quic_congestion` | `"bbr"` | 送信 QUIC の方式。bbr、cubic、new-reno |

## メモリとウィンドウ

予算は接続に約束したリソースを管理します。同じ認証情報を使う接続はグループ予算を共有します。`memory_mib` は 16–16384 MiB、グループは 16 MiB 以上でプロセス予算以下です。ウィンドウは 1–64 MiB を指定し、予算で制限されます。これは論理的な予約量であり、初期一括割り当てや RSS 上限ではありません。カーネル、アロケーター、握手、他サービスの余裕を残します。

## mux と輻輳制御

`adaptive_mux` は `mux = true` の新規セッションに作用します。リソース確保後、消費量と往復時間に応じてウィンドウを増やします。`mux = false` は Vision のままです。両端の互換性を保ってください。`quic_congestion` は QUIC 送信の `bbr`、`cubic`、`new-reno` を選び、TCP は OS が管理します。

## パディング

`default` は各方向の最初の 16 回の業務書き込みの前後に 100–1400 バイトのランダムフレームを加え、その後は 32 回ごとに加えます。`none` で無効化します。`early=N,min=N,max=N,later=N` で変更し、`later=0` で後半を無効にできます。`min <= max`、`max <= 65535` が必要で、初期パディング有効時の最大値はゼロにできません。追加の帯域を消費します。

## ClientHello の書き込み

`segment` は閾値 64 バイト、最初の断片 32 バイトです。`off` は通常の書き込み、`segment:threshold=N,first=M` はカスタム値です。Geneva は受理しません。

```toml
padding_scheme = "default"
tcp_evasion = "segment"
```

これらはトップレベルのフィールドなので、`[performance]` より前に置きます。

## 診断

サーバーで `diagnostics_interval_secs` を 1–3600 秒にすると収集・報告し、ゼロで両方無効になります。外側と宛先のバイト数を分け、アドレス、SNI、認証情報、内容を除きます。実メモリは OS 指標で、宛先への配達は宛先側で確認します。poll の経過時間は CPU 使用率ではありません。関連する設定を一組ずつ変更してください。
