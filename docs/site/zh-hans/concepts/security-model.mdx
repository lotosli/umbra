Umbra 的安全设计围绕三个方面展开：验证连接身份、保护传输中的数据，以及让未认证连接获得真实网站的响应。部署者负责保管密钥、维护设备，并选择可信的服务器环境。

## 认证与站点掩护

服务端在发送首个响应前检查认证信息。通过认证的连接进入代理通道，其他连接转发到配置的真实网站。客户端也会验证服务端临时证书的绑定信息，确认连接的是预期的 Umbra 服务端。

服务端使用受容量和有效期约束的反重放缓存，检查重复认证信息。密码学校验使用常量时间比较，秘密数据通过专用封装管理和清理。

## 保管密钥与客户端配置

`private_key` 和 `mldsa_seed` 只保留在服务端。客户端所需的配置通过可信渠道传递；限制配置文件的读取权限，公开日志和问题报告中去除身份信息。

## 限制本地代理的访问范围

本地 SOCKS5 入口没有用户名密码认证，按示例绑定 `127.0.0.1:1080`。若需要供其他设备使用，应先设置网络访问控制，再调整监听地址。

## 保留应用自身的加密

继续通过 HTTPS 等方式访问目标服务。Vision 在满足条件后转发的仍是应用已经加密的数据。设备安全、浏览器账户和目标服务的可信程度，需要分别管理。

## 站点掩护可以保护什么

真实站点回落让普通访问和未认证探测获得网站响应。观察者仍可能看到连接地址、时间、流量大小等信息，并结合网络条件分析连接。服务器 IP 也可能被直接封锁。Umbra 是自建代理传输工具，不提供多跳匿名网络的身份隔离。

## 浏览器握手档案

当前 `chrome-latest` 使用 Chrome 150 档案；仓库另有 Chrome 153 的 TCP/QUIC 抓包记录。档案用于构建特定握手特征，抓包和 JA3/JA4 等检查覆盖各自的验证项目。目前尚未验证与当前 Chrome 的完整网络行为一致。

## 后量子算法的使用范围

ML-DSA-65 用于临时证书公钥的签名绑定。混合密钥交换路径包含 X25519 与 ML-KEM-768，实际使用取决于协商结果。

当前标准 CLI 的目标探测使用 ring 提供者，不支持 ML-KEM；服务端会跟随探测到的协商组。因此，默认部署应按当前实际协商能力评估，不能仅凭代码中包含 ML-KEM 就视为已启用完整后量子保护。

## 版本与安全报告

当前版本为 **1.0.0-alpha**，尚无独立安全审计完成的公开依据。评估重要用途时，请结合当前实现、版本记录和实际部署条件。

发现安全问题后，先查看仓库的 [Security 页面](https://github.com/lotosli/umbra/security)，按其中可用的报告方式联系维护者。公开讨论中不要附上可利用的漏洞细节、真实凭证或敏感部署信息。
