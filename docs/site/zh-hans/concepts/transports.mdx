应用发出的请求可以是 TCP 或 UDP。Umbra 再按配置选择如何把请求送到服务器：`transport` 决定 TCP 请求的传输，`udp_transport` 可单独指定 UDP 请求的传输；省略后者时，两者使用同一种方式。


## 这一步完成后，你应该看到什么

第一次使用先选 TCP。只有在两端 TCP 配置已验证后，再启用 QUIC 或拆分 TCP/UDP 路径。每次只改一个选项，并用同一个应用复测；当前不会自动切换到另一种传输。

## 从哪种模式开始

| 需求 | 配置起点 | 使用条件 |
| --- | --- | --- |
| 完成首次连接 | `transport = "tcp"` | 服务端 TCP 端口可达，默认启用连接复用 |
| 减少多个请求的重复建连 | TCP + `mux = true` | 多个请求共享外层 TCP 连接 |
| 减少适用 HTTPS 流量的重复加密 | TCP + `mux = false` | 使用独立 Vision 连接 |
| 尝试 UDP 上的传输路径 | `transport = "quic"` | UDP 可达，服务端与掩护网站均支持 QUIC |
| TCP 使用 Vision，UDP 使用 QUIC | TCP + `udp_transport = "quic"` + `mux = false` | 服务端同时启用 TCP、UDP 监听 |

先验证连通性，再比较实际应用的延迟、稳定性与吞吐。切换模式通过修改配置完成。

## TCP 连接复用

```toml
transport = "tcp"
mux = true
```

多个请求共享一条加密连接，减少重复建连。自适应流控根据数据消耗和往返时间调整窗口，并遵守内存预算。

共享 TCP 连接发生丢包时，其中的请求可能一起等待重传。是否启用复用，可根据实际并发请求的表现选择。使用自适应 mux 时，两端版本需兼容。

## 独立 TCP / Vision

```toml
transport = "tcp"
mux = false
```

每个请求使用独立连接。对符合条件的 TLS 1.3 流量，双方完成认证协商后直接转发应用已经加密的 TLS 记录，省去后续外层重复加密与额外封装。其他流量继续使用加密通道。

因此应继续使用应用自身的 HTTPS。当前转发在用户态完成，具体吞吐还取决于设备和网络路径。

## QUIC

```toml
transport = "quic"
```

QUIC 运行在 UDP 上，提供一条不依赖 TCP 连接的传输路径。在 TCP 经常遭遇 RST 重置、UDP 仍可用的环境中，可以尝试这一模式。

服务端需要开启 `udp_listen`、开放对应 UDP 端口，并能连接真实网站的 QUIC 服务。不同 QUIC 流可分别处理重传；同一可靠流仍按顺序交付数据。Umbra 当前也将 UDP 关联数据放在可靠 QUIC 流中，丢包时该流可能等待重传。

默认拥塞控制为 Quinn BBR，也可选择 `cubic` 或 `new-reno`。这些配置作用于本端 QUIC 发送，与系统的 TCP 拥塞控制分开管理。

## 一个入口，同时使用两条路径

将下面片段合并到完整客户端配置：

```toml
transport = "tcp"
udp_transport = "quic"
mux = false
socks_listen = "127.0.0.1:1080"
```

服务端同时配置：

```toml
listen = "0.0.0.0:443"
udp_listen = "0.0.0.0:443"
```

应用仍然只连接一个本地 SOCKS5 入口。Clash 类客户端的 `udp: true` 用于启用 UDP 请求，TCP 请求继续按 `transport` 选择路径。

如果网络条件变化，需要手动修改传输设置；当前没有自动 TCP/QUIC 故障切换。

## 填充和握手分块

`padding_scheme = "default"` 在连接早期加入随机长度的填充数据，之后降低频率，用于弱化固定的数据长度特征，同时会增加带宽开销。

`tcp_evasion = "segment"` 将 TLS ClientHello 分成有序的应用写入。最终 TCP 数据包如何分段仍由操作系统决定。遇到兼容性问题时，可单独测试 `off`。当前配置不支持 Geneva DSL。

具体参数与调整方法见[性能与传输参数](/zh-hans/docs/reference/configuration/)。
