Umbra 的安全設計圍繞三個方面展開：驗證連線身分、保護傳輸中的資料，以及讓未認證連線獲得實際網站的回應。部署者負責保管金鑰、維護裝置，並選擇可信的伺服器環境。

## 認證與網站掩護

伺服器端在發送首個回應前檢查認證資訊。通過認證的連線進入代理通道，其他連線轉發到設定的實際網站。用戶端也會驗證伺服器端暫時憑證的繫結資訊，確認連線的是預期的 Umbra 伺服器端。

伺服器端使用受容量和有效期約束的重送防護快取，檢查重複認證資訊。密碼學驗證使用常數時間比較，秘密資料通過專用封裝管理和清理。

## 保管金鑰與用戶端設定

`private_key` 和 `mldsa_seed` 只保留在伺服器端。用戶端所需的設定透過可信管道傳遞；限制設定檔案的讀取權限，公開紀錄和問題報告中去除身分資訊。

## 限制本機代理的存取範圍

本機 SOCKS5 入口沒有使用者名稱密碼認證，依照範例繫結 `127.0.0.1:1080`。若需要供其他裝置使用，應先設定網路存取控制，再調整接聽位址。

## 保留應用程式自身的加密

繼續透過 HTTPS 等方式存取目標服務。Vision 在滿足條件後轉發的仍是應用程式已經加密的資料。裝置安全、瀏覽器帳戶和目標服務的可信程度，需要分別管理。

## 網站掩護可以保護什麼

實際網站轉送讓一般瀏覽和未認證探測獲得網站回應。觀察者仍可能看到連線位址、時間、流量大小等資訊，並結合網路條件分析連線。伺服器 IP 也可能被直接封鎖。Umbra 是自建代理傳輸工具，不提供多跳匿名網路的身分隔離。

## 瀏覽器握手設定檔

目前 `chrome-latest` 使用 Chrome 150 設定檔；儲存庫另有 Chrome 153 的 TCP/QUIC 封包擷取記錄。這些設定檔用來建置特定的握手特徵，封包擷取和 JA3/JA4 等檢查涵蓋各自的驗證項目。目前尚未驗證與最新版 Chrome 的完整網路行為一致。

## 後量子演演算法的使用範圍

ML-DSA-65 用於暫時憑證公開金鑰的簽章繫結。混合金鑰交換路徑包含 X25519 與 ML-KEM-768，實際使用取決於協商結果。

目前標準 CLI 的目標探測使用 ring 提供者，不支援 ML-KEM；伺服器端會跟隨探測到的協商組。因此，預設部署應按目前實際協商能力評估，不能僅憑程式碼中包含 ML-KEM 就視為已啟用完整後量子保護。

## 版本與安全報告

目前版本為 **1.0.0-alpha**，尚無獨立安全稽核完成的公開依據。評估重要用途時，請結合目前實作、版本記錄和實際部署條件。

發現安全問題後，先查看儲存庫的 [Security 頁面](https://github.com/lotosli/umbra/security)，按其中可用的報告方式聯繫維護者。公開討論中不要附上可利用的漏洞細節、真實認證資訊或敏感部署資訊。
