應用程式發出的請求可以是 TCP 或 UDP。Umbra 再按設定選擇如何把請求送到伺服器：`transport` 決定 TCP 請求的傳輸，`udp_transport` 可單獨指定 UDP 請求的傳輸；省略後者時，兩者使用同一種方式。

## 從哪種模式開始

| 需求 | 設定起點 | 使用條件 |
| --- | --- | --- |
| 完成第一次連線 | `transport = "tcp"` | 伺服器端 TCP 連接埠可達，預設啟用連線重複使用 |
| 減少多個請求的重複建連 | TCP + `mux = true` | 多個請求共享外層 TCP 連線 |
| 減少適用 HTTPS 流量的重複加密 | TCP + `mux = false` | 使用獨立 Vision 連線 |
| 嘗試 UDP 上的傳輸路徑 | `transport = "quic"` | UDP 可達，伺服器端與掩護網站均支援 QUIC |
| TCP 使用 Vision，UDP 使用 QUIC | TCP + `udp_transport = "quic"` + `mux = false` | 伺服器端同時啟用 TCP、UDP 接聽 |

先驗證連通性，再比較實際應用程式的延遲、穩定性與吞吐。切換模式通過修改設定完成。

## TCP 連線重複使用

```toml
transport = "tcp"
mux = true
```

多個請求共享一條加密連線，減少重複建連。自適應流控根據資料消耗和往返時間調整視窗，並遵守記憶體預算。

共享 TCP 連線發生丟包時，其中的請求可能一起等待重傳。是否啟用重複使用，可根據實際併發請求的表現選擇。使用自適應 mux 時，兩端版本需兼容。

## 獨立 TCP / Vision

```toml
transport = "tcp"
mux = false
```

每個請求使用獨立連線。對符合條件的 TLS 1.3 流量，雙方完成認證協商後直接轉發應用程式已經加密的 TLS 記錄，省去後續外層重複加密與額外封裝。其他流量繼續使用加密通道。

因此應繼續使用應用程式自身的 HTTPS。目前轉發在使用者態完成，具體吞吐還取決於裝置和網路路徑。

## QUIC

```toml
transport = "quic"
```

QUIC 執行在 UDP 上，提供一條不依賴 TCP 連線的傳輸路徑。在 TCP 經常遭遇 RST 重置、UDP 仍可用的環境中，可以嘗試這一模式。

伺服器端需要開啟 `udp_listen`、開放對應 UDP 連接埠，並能連線實際網站的 QUIC 服務。不同 QUIC 流可分別處理重傳；同一可靠流仍按順序交付資料。Umbra 目前也將 UDP 關聯資料放在可靠 QUIC 流中，丟包時該流可能等待重傳。

預設擁塞控制為 Quinn BBR，也可選擇 `cubic` 或 `new-reno`。這些設定作用於本端 QUIC 發送，與系統的 TCP 擁塞控制分開管理。

## 一個入口，同時使用兩條路徑

將下面片段合併到完整用戶端設定：

```toml
transport = "tcp"
udp_transport = "quic"
mux = false
socks_listen = "127.0.0.1:1080"
```

伺服器端同時設定：

```toml
listen = "0.0.0.0:443"
udp_listen = "0.0.0.0:443"
```

應用程式仍然只連線一個本機 SOCKS5 入口。Clash 類用戶端的 `udp: true` 用於啟用 UDP 請求，TCP 請求繼續按 `transport` 選擇路徑。

如果網路條件變化，需要手動修改傳輸設定；目前沒有自動 TCP/QUIC 故障切換。

## 填充和握手分塊

`padding_scheme = "default"` 在連線早期加入隨機長度的填充資料，之後降低頻率，用於弱化固定的資料長度特徵，同時會增加帶寬負擔。

`tcp_evasion = "segment"` 將 TLS ClientHello 分成有序的應用程式寫入。最終 TCP 資料包如何分段仍由操作系統決定。遇到兼容性問題時，可單獨測試 `off`。目前設定不支援 Geneva DSL。

具體參數與調整方法見[效能與傳輸參數](/zh-hant/docs/reference/configuration/)。
