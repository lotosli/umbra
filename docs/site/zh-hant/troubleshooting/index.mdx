先記錄兩端版本、平台和錯誤資訊，再用一個簡單請求復現。一次只修改一個設定，便於確認問題在哪一段。


## 完成這一步後，如何確認成功

先找出失敗的位置：連接 127.0.0.1:1080 遭拒時檢查本機用戶端；遠端連線逾時時檢查伺服器程序、位址和連接埠；交握失敗時核對金鑰、short_id、server_name 與兩端時鐘。修正後先重跑 curl，再回到應用程式驗證。

## 先做一次直接連線測試

```sh
umbra --help
curl --socks5-hostname 127.0.0.1:1080 https://example.com/
```

如果直接使用 SOCKS5 可以存取，而通過規則用戶端失敗，優先檢查節點選擇、分流規則、DNS 和代理循環。

## 伺服器端啟動後立即結束

檢查 TOML 語法、必填欄位、檔案讀取權限和接聽連接埠衝突。啟動時會探測掩護網站；同時檢查 `dest`、網站名稱和伺服器到該網站的連線。

## 用戶端無法認證

透過可信管道核對 `public_key`、`mldsa_verify`、`short_id` 和 `server_name`，並確認對應的是正在執行的伺服器端設定。

檢查兩端系統時間，先修正時鐘，再評估時間容差。隨後檢查用戶端能否存取實際設定的伺服器連接埠。

## 應用程式仍然無法存取

確認應用程式確實使用 `127.0.0.1:1080` 的 SOCKS5 代理。再檢查伺服器端到應用程式目標的 DNS 和網路連線。使用 `socks5h` 或 `--socks5-hostname` 測試時，網域名稱會交給代理處理。

## TCP 正常，UDP 失敗

檢查用戶端的 `udp_transport`。使用 QUIC 時，確認伺服器端已啟用 `udp_listen`、防火牆允許 UDP，而且 `dest` 提供可達的真實 QUIC/HTTP/3 服務。

在規則用戶端中啟用 UDP，並測試實際 UDP 應用程式。瀏覽網頁通常只能驗證相應的網頁連線路徑。

## 連線到的是掩護網站

普通瀏覽器或未認證 TLS 探測收到掩護網站的憑證和回應，屬於預期行為。驗證代理功能時，請使用設定正確的 Umbra 用戶端和本機 SOCKS5 入口。

## 連線可用，但速度不理想

保持相同目標、負載和網路路徑，對比不同傳輸設定。必要時開啟數值診斷，觀察視窗、排隊和記憶體預算，並結合系統 CPU、記憶體指標判斷。具體解釋見[效能與傳輸參數](/zh-hant/docs/reference/configuration/)。

## 提交問題時提供什麼

提供版本、操作系統、失敗階段、脫敏後的指令與錯誤類別，以及最小復現步驟。分享前移除金鑰、憑據、實際部署位址和使用者內容。涉及安全漏洞時，按[安全模型](/zh-hant/docs/concepts/security-model/)中的方式報告。
